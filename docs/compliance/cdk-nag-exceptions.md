# cdk-nag NIST 800-53 rev 5 exceptions register

> **Draft, pending review by the agency ISO.** Nothing is deployed. These are engineering decisions recorded so a reviewer can accept, reject or schedule each one.

`infra/bin/relay.ts` applies the cdk-nag `NIST80053R5Checks` pack (cdk-nag 2.38.2) to every stack. An unsuppressed finding is an error, so `cdk synth` fails, and `infra/test/nag.test.ts` synthesizes dev and prod and fails on any unsuppressed NIST error or warning. `-c nag=off` skips the pack for quick local synths only.

Every exception below is a `NagSuppressions.addResourceSuppressions` call in `infra/lib/compliance.ts`, scoped to the named resources (there is no stack-wide suppression; a test checks that). The code resolves each resource by its construct path and throws if it is gone, so this register cannot silently drift from the infrastructure. A new resource that trips a rule fails synth until it is fixed or added here.

Controls are the ones cdk-nag maps to the rule (from its report); the list is abridged to the families that matter for each decision.

## Findings before and after

| Synth | Unsuppressed before (no fixes) | Unsuppressed after | Suppressed after (rule x resource) | Of those, on resources the fixes added |
| ----- | ------------------------------ | ------------------ | ---------------------------------- | -------------------------------------- |
| dev   | 130                            | 0                  | 89 (13 rules)                      | 8                                      |
| prod  | 122                            | 0                  | 80 (11 rules)                      | 8                                      |

So the fixes below cleared 49 findings on dev and 50 on prod; the rest are the exceptions in this register. The 8 findings on new resources are the two VPC flow-log roles (IAMNoInlinePolicy) and the three access log buckets (S3BucketReplicationEnabled, S3DefaultEncryptionKMS). Dev has two more rules than prod because dev deliberately has no PITR, no deletion protection and no reserved concurrency.

The raw lists (rule, stack, resource) were captured on 2026-11-10 from `npm run synth -w @relay/infra` (dev) and `npx cdk synth -c stage=prod -c alarmEmail=... -c publicAlertBaseUrl=...` (prod); cdk-nag also writes them as CSV to `infra/cdk.out/NIST.800.53.R5-*-NagReport.csv` on every synth.

## Encryption at rest: keys

Four customer-managed symmetric keys per stage (`infra/lib/encryption.ts`), grouped by data domain, plus the existing asymmetric alert-signing key:

| Alias                           | Region    | Stack  | Encrypts                                                                     |
| ------------------------------- | --------- | ------ | ---------------------------------------------------------------------------- |
| `alias/relay/<stage>/data`      | us-west-2 | config | DynamoDB tables, Aurora storage, raw and zone-pack buckets, every secret     |
| `alias/relay/<stage>/messaging` | us-west-2 | config | every SQS queue, the alerts SNS topic                                        |
| `alias/relay/<stage>/logs`      | us-west-2 | config | every CloudWatch log group, the CloudTrail trail and its bucket              |
| `alias/relay/<stage>/edge`      | us-east-1 | edge   | public-alerts bucket (read by CloudFront OAC), edge SNS topic, WAF log group |

All four rotate automatically every 365 days and are retained on prod (`RemovalPolicy.RETAIN`, 30-day deletion window); dev keys are destroyed with the stack (7-day window). `encryptResources` walks each finished stack and points every table, cluster, bucket, secret, queue, topic, log group and trail at its key, so a resource added later is encrypted without anyone passing a key; `infra/test/encryption.test.ts` checks every resource of those types.

Key policies keep the account-root statement (IAM administers the keys) and, like the AWS-managed keys they replace, let principals of this account use a key only through the services that hold the data (`kms:CallerAccount` plus `kms:ViaService`). Access to the data is still decided by each resource's IAM grant (`grants.ts`). Service principals that write on their own get narrow statements: CloudWatch Logs (this account's log groups in the region), CloudTrail (this account's trails), CloudWatch alarms, EventBridge, Budgets and Cost Anomaly Detection (publishing to the encrypted topics), and CloudFront for OAC reads. The CloudFront statement is limited to this account's distributions (`distribution/*`) because naming the one distribution would create a dependency cycle (distribution, bucket, key); CDK's own OAC helper makes the same trade-off. A tighter option, per-principal key grants instead of `ViaService`, is possible later.

Not moved to a customer-managed key, and why:

- S3 access log buckets: S3 requires SSE-S3 for server access log targets (exception above).
- The us-east-1 replica of `relay/<stage>/origin-verify` uses the AWS-managed `aws/secretsmanager` key in us-east-1. Giving it the edge key would need that key to exist before the config stack deploys, but the edge stack deploys last. The primary (read by the API) uses the data key.
- RDS enhanced monitoring writes to the account-wide `RDSOSMetrics` log group, which RDS creates and Relay does not own.
- Lambda environment variables keep the default Lambda service key (no secrets are in them; secrets are fetched from Secrets Manager).
- There are no SSM SecureString parameters: the only parameter is the kill switch, a plain `String`.

**Cost.** KMS charges $1 per key per month, plus $1 per month for each of the first two rotations (no charge after the second), and $0.03 per 10,000 requests after a free tier of 20,000 requests per month ([AWS KMS pricing](https://aws.amazon.com/kms/pricing/), fetched 2026-11-10). For the four new keys: $4/month per stage in year one, $8 in year two, $12 from year three. Requests stay small because S3 Bucket Keys, the 5-minute SQS data key reuse, DynamoDB and CloudWatch Logs all cache data keys; estimated under $2/month per stage at pilot volume (an estimate, not measured). The existing alert-signing key ($1/month) is unchanged.

## FIPS 140 endpoints

`-c fips=true|false` (default: on for prod, off for dev) sets `AWS_USE_FIPS_ENDPOINT=true` on every Relay Lambda except the API function, and on the sender container (`encryption.ts`, `useFipsEndpoints`). The AWS SDK for JavaScript v3 applies that variable to every client in the process, so a function may only get it when every AWS service it calls has a FIPS endpoint in its region.

| Service the backend calls                       | FIPS endpoint in us-west-2 and us-east-1                                              | Source                                                                                                                                                                                                                                                        |
| ----------------------------------------------- | ------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| DynamoDB (and Streams)                          | Yes: `dynamodb-fips.us-west-2.amazonaws.com`, `dynamodb-fips.us-east-1.amazonaws.com` | [DynamoDB endpoints](https://docs.aws.amazon.com/general/latest/gr/ddb.html)                                                                                                                                                                                  |
| RDS Data API                                    | Yes: `rds-data-fips.<region>.amazonaws.com`                                           | [Data API endpoints](https://docs.aws.amazon.com/AmazonRDS/latest/AuroraUserGuide/data-api.ipv6.html) gives the pattern and names `rds-data-fips.us-east-1.api.aws`; us-west-2 is confirmed by the `fips-us-west-2` variant in botocore 1.34.22 endpoint data |
| SQS, Secrets Manager, KMS, SSM, Lambda, ECS, S3 | Yes in both regions                                                                   | FIPS variants in botocore 1.34.22 `endpoints.json` (local copy shipped with the Google Cloud SDK); not re-checked against the live AWS FIPS page, which could not be fetched                                                                                  |
| Amazon Location Service                         | **No** (FIPS only in GovCloud us-gov-west-1)                                          | [Location endpoints](https://docs.aws.amazon.com/general/latest/gr/location.html)                                                                                                                                                                             |

So the API Lambda (it calls Amazon Location for place search) does not get the variable; its other calls use standard endpoints, still over TLS 1.2+. Not verified: whether the sender VPC's DynamoDB gateway endpoint routes the FIPS hostname (if not, that traffic goes through the internet gateway, still over TLS). APNs, FCM and Expo are external services, not AWS FIPS endpoints. Before relying on this for an ATO, re-check each service against the current [AWS FIPS page](https://aws.amazon.com/compliance/fips/), which was not reachable from the build environment on 2026-11-10.

## Open items for the project owner

- Accept or reject each exception above (ISO).
- Decide whether automatic Aurora credential rotation is worth about $15/month per stage (VPC endpoint plus a VPC rotation Lambda).
- Get a custom domain and ACM certificate for the edge so viewers are held to TLS 1.2.
- Decide on an AWS Backup plan and cross-region replication once the State's retention and the RPO are set.
- Trail bucket Object Lock (AU-9, `b2-hardening`): governance mode, default retention 365 days on prod and 1 on dev (`-c trailObjectLockDays`). Object Lock is enabled when the bucket is created and can never be turned off afterwards, so pick the mode and default before the first prod deploy; changing the retention later only affects new objects. Governance mode still lets a principal with `s3:BypassGovernanceRetention` (any account administrator today) delete versions, with an explicit header that CloudTrail records. Decide whether prod should use compliance mode (nobody, root included, can delete inside the window) or move the trail to a log-archive account (S-06).
- Key-state events (`DisableKey`, `ScheduleKeyDeletion`, `PutKeyPolicy`, alias changes) of the data, messaging and logs keys now alert the alerts topic (`DataKeyChangedRule`, added at the 2026-11 review). The edge key in us-east-1 is covered on `b2-hardening` by `EdgeKeyChangedRule` and `EdgeKeyAliasChangedRule` in the edge stack (EventBridge rules are regional), which notify the edge topic; the edge key policy gained `AllowEventBridgeRules` for that.
- cdk-nag evaluates `AWS::Lambda::Function` resources created through `aws-lambda` only; the provider Lambdas of CDK's own custom resources (cross-region exports, `restrictDefaultSecurityGroup`, dev `autoDeleteObjects`) are not checked ([review](./review-2026-11.md), B3). Their logs (C6) are fixed on `b2-hardening`: each provider Lambda gets a declared log group (stage retention, logs or edge key, retained on prod) through `LoggingConfig.LogGroup` (`infra/lib/provider-logs.ts`), so Lambda no longer creates a `/aws/lambda/<generated name>` group without retention or CMK; `infra/test/provider-logs.test.ts` asserts it for every Lambda in every stack. The cross-region export providers are created by CDK only after every aspect has run, so their groups are declared up front and attached by a validation hook, which fails synth if a provider appears without a group. What stays CDK's: the providers' runtime, role, timeout and code (no VPC, DLQ, reserved concurrency or FIPS endpoint setting), which Relay does not override.
