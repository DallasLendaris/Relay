## 1. Cancellation and update follow-ups (`b2-cancel`)

What holds up under scrutiny:

- **The Cancel tombstone cannot hit another alert or a newer version.** Tombstoned keys are `alertId:previousSeverity:cell:bucket` (`backend/src/scale/fanout/keys.ts` `bucketKey`), so they are scoped to this alert's id. They are written only for a `cancel` request (`backend/src/scale/fanout/follow-up.ts:219`), and lifecycle treats a stored Cancel as final: later Updates and Alerts that reference it are ignored (`backend/src/ingest/lifecycle.ts`, "alert already cancelled"), and a real Cancel clears the feed-absence marker so restoration cannot bring the alert back (`backend/src/ingest/poll.ts`, `clearEnded`). No newer Update can therefore reuse a tombstoned key. Update follow-ups never tombstone, which is right: a later Update that re-adds a dropped cell with the same severity reuses the same key.
- **Loudness.** `cancel` and `removed` are always quiet (`backend/src/delivery/follow-up.ts:76`); the sender reads the kind from the key, so retries and re-checks (`:r`, `:v`, `:h`, `:u`, `:s`) stay quiet.
- **Exactly once.** Follow-up keys are deterministic per (version tag, kind, cell, bucket), so a replayed Cancel, a re-plan and a shard re-run collapse at the sender's claim. Member sets are per cell, and the normal fan-out puts a multi-cell device in one cell only, so a device gets one follow-up.
- **Version comparisons.** Planner, shard worker and sender all require the alert's current `sourceId` tag and the right state (`followUpRefusal`), and the sender re-reads once on `stale_version` before acking. An Update follow-up still queued when a Cancel lands is dropped.
- **Migration 0015 and the 0011 edit.** Migrations are recorded by name in `schema_migrations` (`backend/src/db/sql.ts`), so the 0011 edit never runs through the migrator on an existing database. That is intended: `infra/scripts/db-roles.ts` re-applies 0011 on every run, and 0011 starts with `REVOKE ALL`, so the table **must** be listed there or the next db-roles run strips 0015's grants. 0015 grants by itself (guarded on the roles existing), and `backend/test/db/dropped-cells.test.ts` checks both paths. Safe on an existing database (`CREATE TABLE IF NOT EXISTS`, FK with cascade, no backfill needed). The only problem was that the migrations README forbids editing a merged migration without naming this exception (fixed, below).

## 2. Agency auth (`b2-agency`)

Checked and sound: the pool requires TOTP (`Mfa.REQUIRED`, no SMS or email), self sign-up is off, the only client is SRP-only with no OAuth; the JWT authorizer pins this pool and client, and the function re-checks `token_use=access`, `client_id` and `iss` (`backend/src/agency/principal.ts`), so tokens from another pool or client, or ID tokens, are refused. Custom claims cannot be forged (signed tokens) and the pre-token trigger copies only `custom:agency_id` / `custom:jurisdiction` from Cognito's own user record; the client's `writeAttributes` excludes both (only `locale`, `timezone`), so nothing the user can write reaches the token. Jurisdiction parsing is all-or-nothing, ASCII digits only (`^06\d{3}$`, odd county numbers), trims and dedupes, and any requested county outside the jurisdiction refuses the whole request; API Gateway joins repeated `areas` parameters with commas, which go through the same check. relay-admin cannot read summaries. The audit write happens before the response and any failure (including an invalid key) returns 503; S3 PutObject is allowed on the prefix for the function only, the bucket policy denies PutObject to every other principal and denies delete or retention changes to all but the break-glass role, and the logs key allows S3 use by in-account callers, so the function can write. CloudFront caches nothing on `/agency/*` and forwards `Authorization` (AWS: with caching off, the AllViewer policies forward it, [re:Post](https://repost.aws/knowledge-center/cloudfront-authorization-header)).

## 3. Deploy workflow (`b2-deploy`)

Checked and sound: no `pull_request` / `workflow_run` triggers, so forks and PRs get no OIDC token; each role's trust is `StringEquals` on both `aud = sts.amazonaws.com` and `sub = repo:DallasLendaris/Relay:environment:<env>` (`infra/bootstrap/github-deploy-stack.ts`), so a `dev` or `dev-diff` token cannot assume a prod role; actions are SHA-pinned; the artifact is uploaded and downloaded by name inside one run (artifacts are run-scoped and immutable per name, and download-artifact verifies the digest), and the deploy job never re-synthesizes. ## 4. Hardening and zod 4 (spot-check)

- **NWS date-times.** NWS CAP 1.2 specifies `YYYY-MM-DDThh:mm:ssXzh:zm`, e.g. `2011-05-24T16:49:00-07:00` ([NWS CAP v1.2 guide](https://www.weather.gov/media/alert/CAP_v12_guide_03-07-2017.pdf)), and the API states "All times generated by the API are in ISO-8601 format" ([NWS API docs](https://www.weather.gov/documentation/services-web-api)). zod 4's `z.iso.datetime({ offset: true })` accepts exactly that, `Z`, fractional seconds and CAP's UTC form `-00:00` (verified; now pinned in `packages/shared/test/zod4-semantics.test.ts`). It rejects missing seconds and colon-less offsets, which neither spec allows. **The rejection is safe for conforming feeds.** Note H-1: a malformed optional time (`onset`, `ends`) rejects the whole alert (`backend/src/ingest/normalize.ts:102`, unchanged behaviour); for a safety product, consider dropping the bad optional field with a warning instead of losing the warning itself, and make sure normalize rejections alarm.
- Origin domain path, provider log groups, edge key rules, trail Object Lock (H-2 note: adding Object Lock to an existing bucket is a replacement in CloudFormation; harmless now because nothing is deployed), `retryAttempts: 0` with `maxEventAge`, PausedConsumer `maxConcurrency` 10, worker log redaction: no defects found.
